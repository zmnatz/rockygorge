# Proposed: pull the nightly CMS data in the build, not in a committed snapshot

## Status

Proposed. Not implemented; tracked in the issue linked from the PR that added this file.

## Context

Since ADRs 014 and 016, pages are generated by Netlify's Next.js runtime, and what can be calculated from the committed match archive is calculated at build time (the player histories, the scoring leaders). What still comes from the CMS is pulled by a GitHub workflow (`update-snapshots.yml`, daily 06:00 UTC) and **committed**: `public/data/scores.json`, `standings/`, `club-pages.json`, `public/crests/` and the match archive `.cache/matches/`. That commit is also what triggers the nightly Netlify build.

The costs of that arrangement:

- A bot commit to `master` every night the data changes, and merge conflicts when a branch or PR touches the same files (#234 needed one).
- Derived data can drift from its source (the committed leaders were a day behind the standings).
- The deploy is tied to a commit: nothing can refresh data without one.

## Options

1. **Build-time pull with a persisted cache.** A scheduled trigger (a GitHub Actions cron calling a Netlify build hook, or a Netlify scheduled function) starts a build; `bun run build:data` first runs the generators online, keeping their state (the archive's locked seasons, the saved standings seasons, crests) in `.next/cache`, which Netlify saves between builds, as the eligibility site does for its Locked Seasons (its ADR 019). A cache miss means a full-history pull (a dozen batched match requests, plus every club feed for standings).
2. **Pull on request with `revalidate`.** The pages fetch the CMS themselves. Rejected for the large pulls (every club feed, every match), which the CMS's rate limit (500 requests per IP) and the function time limit don't suit. It could suit `scores.json` alone.
3. **Keep committing** (today). Nothing to build or risk; the costs above stay.

## Recommendation

Option 1, after settling the following, which are why it isn't done yet:

- **Failure behaviour.** Today a failed job keeps its previous snapshot and the others still commit. In a build, a CMS outage or 429 would fail the deploy (the previous deploy stays live) unless each generator falls back to the cached copy.
- **Which builds pull.** Pushes and deploy previews shouldn't each hit the CMS. The pull should run only for the scheduled build (or when the cache is older than a day), and other builds reuse the cache.
- **A cold cache.** A full pull has to fit the build's time limit, and the standings pull is the slow one (it reads every playing club's feed, three at a time).
- **The trigger.** A Netlify build hook is a secret held outside the repo; someone has to create it and the GitHub Actions secret.
- **Crests.** `public/crests/` is binary and committed; it would move into the same cache.

Until then, ADR 016's build-time calculation covers everything that can be derived from the archive.
